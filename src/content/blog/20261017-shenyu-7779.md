`/files/a%2Fb` 里的 `%2F` 是一个转义过的斜杠，表示「这个斜杠属于文件名」，不是路径分隔符。请求经过 RequestPlugin 之后，路径变成了 `/files/a%252Fb`——`%` 自己也被转义了一次。下游拿到的文件名从 `a/b` 变成了 `a%2Fb`。

触发条件更值得注意：那条规则只设置了 `X-Demo` 请求头，没有碰路径，也没有碰查询参数。

对应 Issue [#7685](https://github.com/apache/shenyu/issues/7685)，修复是 PR [#7779](https://github.com/apache/shenyu/pull/7779)，改动集中在 `RequestPlugin` 一个类里。

## 没改参数，为什么也重建了 URI

原来的 `doExecute` 把请求头和 URI 放在同一次 `exchange.mutate()` 里改：

```java
.request(originalRequest -> originalRequest.uri(
        UriComponentsBuilder.fromUri(exchange.getRequest().getURI())
                .replaceQueryParams(getQueryParams(request, requestHandle))
                .build()
                .encode()
                .toUri()
        ).headers(httpHeaders -> setHeaders(httpHeaders, request, requestHandle))
)
```

这段代码没有任何「这条规则是否需要改参数」的判断。只要规则命中了插件，URI 就会被拆开、重新拼装、再编码一次。

注意这里的结构：`.headers(...)` 和 `.uri(...)` 是并列的两个动作，但只有后者会改写请求目标。请求头的变化是增量的，URI 的重建是全量的——把一个只需要局部修改的请求，整个替换成了一个新构造的 URI。

## 编码一次是对的，编码两次是错的

`fromUri()` 和 `encode()` 各自都没问题，问题在于它们对同一个字符串的理解不一致。

`UriComponentsBuilder.fromUri(uri)` 把传入的 URI 当作**已经编码好的**，所以 `%2F` 原样保留在 `rawPath` 里。而 `getPath()` 返回的是解码后的 `/files/a/b`。同一个 URI 对象，两个 getter，两种表示。

后面的 `.encode()` 负责把**未编码的组件**编码成合法 URI。但它面对的组件来自 `rawPath`，于是把 `%` 当成一个普通字符，编码成 `%25`。

| 阶段 | 路径值 | 谁认为它是什么 |
| --- | --- | --- |
| 进入 `fromUri()` | `/files/a%2Fb` | 已编码 |
| `build()` 之后 | `/files/a%2Fb` | 已编码，尚未处理 |
| `encode()` 之后 | `/files/a%252Fb` | 被当成原始值又编了一遍 |

两次编码单独看都是正确操作，叠在一起就错了。判断「要不要编码」不能只看调用了哪个方法，还要看手上这个值处在哪一层。

这个推断不需要靠读源码来相信。PR 里的回归测试就是直接证据——同一个 `URI` 对象，两个 getter 给出两种结果：

```java
assertEquals("/files/a%2Fb", requestUri.getRawPath());  // 已编码
// getPath() 会返回 /files/a/b，转义信息在这一层已经丢失
```

修复后的测试断言 `getRawPath()` 等于 `/files/a%2Fb`。如果编码被重复执行，这一行会变成 `/files/a%252Fb`，测试直接失败。也就是说，「`fromUri()` 把入参当作已编码」这个判断，是被一个会失败的断言固定下来的，而不是一句解释。

## 只编码新加进来的那部分

修法分两步，对应两个不同的问题。

**第一，不需要重建就不重建。** 只有规则确实要改查询参数时才动 URI：

```java
originalRequest.headers(httpHeaders -> setHeaders(httpHeaders, request, requestHandle));
if (Objects.nonNull(requestHandle.getParameter()) && requestHandle.getParameter().isNotEmptyConfig()) {
    originalRequest.uri(buildRequestUri(request, requestHandle));
}
```

只改请求头或 Cookie 的规则现在完全不碰 URI，原来的 `rawPath` 一个字都不变。这不只是省了几次对象构造——不需要发生的转换，就不会引入转换带来的偏差。

**第二，真要重建时，只编码新东西。** 这里要先分清两个来源：

- `request.getQueryParams()` 返回的是**解码后**的值，属于原始值，需要编码；
- `request.getURI()` 里的路径是**已编码**的，不能再碰。

所以把参数单独编码一遍，再用 `build(true)` 告诉 builder「我给你的都是已经编码好的，不要再动」：

```java
MultiValueMap<String, String> encodedQueryParams = new LinkedMultiValueMap<>(queryParams.size());
queryParams.forEach((key, values) -> values.forEach(value -> encodedQueryParams.add(
        UriUtils.encodeQueryParam(key, StandardCharsets.UTF_8),
        UriUtils.encodeQueryParam(value, StandardCharsets.UTF_8))));
return UriComponentsBuilder.fromUri(request.getURI())
        .replaceQueryParams(encodedQueryParams)
        .build(true)
        .toUri();
```

`build()` 和 `build(true)` 只差一个参数，含义却相反：前者表示「我给的还是原始值，请你编码」，后者表示「我给的已经编码好了，原样使用」。选错任何一个，结果都会差一层转义。

这个参数也不是纯粹的开关。选了 `build(true)`，就等于承诺所有组件都合法；如果传进去的值里还有未编码的空格或非 ASCII 字符，构造 URI 时就会失败。`encodeQueryParam` 这一步既是语义上的修正，也是 `build(true)` 能够成立的前提。

已知的一处保留行为：参数规则会把无值的查询参数 `?flag` 重建为 `?flag=`。这与修复前一致，也不影响只改请求头的规则——后者现在根本不重建 URI。

## 断言为什么选 rawPath

回归测试覆盖四种规则：只改请求头、添加参数、删除参数、替换参数。输入统一是 `http://localhost/files/a%2Fb?x=hello%20world`，断言统一检查 `getRawPath()`：

```java
assertEquals("/files/a%2Fb", requestUri.getRawPath());
assertEquals("x=hello%20world&added=a%20b", requestUri.getRawQuery());
```

用 `getRawPath()` 而不是 `getPath()` 是关键。`getPath()` 会把 `%2F` 解码成 `/`，`/files/a%2Fb` 和 `/files/a/b` 在它眼里完全一样——而这两种路径在下游是两个不同的资源。要验证「转义有没有被保留」，就必须看原始字符串。这也是为什么上面那段把根因的确认落在 `getRawPath()` 上。

这引出一个更普遍的问题：**断言选在哪个表示上，决定了测试究竟在保护什么。** 如果这四个用例断言的是 `getPath()`，那么即便代码把 `%2F` 编成了 `%252F`，测试依然会全绿。

`added=a%20b` 这一项确认了另一半：新增参数值里的空格被编码了一次，既没有漏掉，也没有变成 `%2520`。

## 从这次修复能带走的两条判断

**一、不需要发生的转换就不要发生。** 老代码的问题不是编码函数用错了，而是在一个不需要改写 URI 的场景里改写了 URI。先把「这一步是否必要」问清楚，很多边界问题根本不会出现。

**二、改一个值之前，先确认它在哪一层。** 同一个请求里，`rawPath` 是已编码内容，`getQueryParams()` 返回解码后的原始值，两者混在一条流水线上，任何一步「顺手编码一下」都会出错。编码函数本身都是对的，错在把它用在了错误层次的输入上。

这两条也可以当成读 diff 时的检查项：这段代码有没有做不必要的事？它处理的值，是原始值还是已编码内容？
