假设一个缓存 key 还没有结果，同时来了十个请求。十个请求各自查询缓存，全部 miss，然后各自向上游发起请求。

这里的缓存没有坏。它只能复用已经保存的结果，而这十个请求到达时，第一个结果还没回来。问题出在「发现没有结果」和「把结果放进缓存」之间的空窗。

Apache ShenYu 在 [apache/shenyu#7969](https://github.com/apache/shenyu/pull/7969) 中增加了 single-flight 协调：符合条件的请求如果同时 miss 同一个 key，先让一个请求负责回源，其余请求等待并复用它捕获的响应。

需要先保留一个限定：这不是「任何情况下，同一个 key 都只能回源一次」的承诺。响应不能共享、等待超时或协调容量不足时，后来的请求仍会独立回源。这些回退不是实现没做完，而是这次设计的一部分。

## 缓存里没有结果，不代表没人正在取结果

原来的查询路径回答的是一个问题：**这个 key 有没有已经存好的响应？**

它没有回答另一个问题：**这个 key 是否已经有请求正在回源？**

两个请求几乎同时到达时，即使第一个请求已经发往上游，第二个请求仍然只能查到空缓存。它不知道前面的工作正在进行，于是又发一次。

缓存中的结果和进行中的工作，是两种不同状态。前者可以跨后续请求复用，后者只在这次填充还没结束时存在。因此，新实现没有拿一个空值假装缓存命中，而是增加了 `ResponseSingleFlight`，单独协调正在填充的 key。

同一个 key 的请求分成两个角色：

- **leader**：取得填充资格，继续执行回源流程，捕获响应并交付结果。
- **follower**：发现已有填充者，等待这次填充的结果；满足共享条件时，把结果写入自己的响应。

这个名字描述的是一次填充中的角色，不是固定的主节点和从节点。一次填充结束后，对应的协调状态需要释放，后续 miss 可以开始新的一轮。

## 选出一个 leader，不能先查再放

如果用「先查进行中的表，没有就插入」来取得资格，两个线程仍可能同时看到空值，然后都认为自己是 leader。

这会把原来的竞争换一个位置，却没有消除它。查询和插入必须是一个原子判断。

这里的关键操作是 `putIfAbsent`：只有 key 尚不存在时，才把当前候选放进去；如果已经存在，返回已有的协调对象。因而请求可以根据插入结果判断自己的角色，而不是根据一次可能已经过时的查询判断。

它协调的粒度是 **key**，不是整个缓存插件。不同 key 仍然可以分别回源，不需要为了一个冷 key，让其他所有请求排队。

key 也没有另外发明一套。single-flight 沿用原来的响应缓存 key：它由 HTTP 方法、完整 URI，以及 selector、rule 的标识共同构成。不同查询参数或不同规则，不会只因为路径一样就被合成同一次填充。

但这个 key **不包含所有请求头**，不能把它解释成能够区分任意两种请求。现有资格判断只让无 body 的 GET 进入缓存路径；带 Authorization、Cookie、Range、条件请求等头的请求会绕过。响应侧还会排除 `Vary` 等不能按这个 key 直接复用的情况。这项改动沿用的是已有缓存边界，不是新建了一套完整的请求等价关系。

这一步保证的是「谁负责这次填充」。它还没有解决下一步：leader 的结果应该怎样交给 follower？

## 共享响应包，不是共享第一个请求的执行过程

在响应式代码里，很容易想到把一个 Mono 缓存下来，让其他请求也订阅它。但这条处理流程可能绑定着第一个请求的 exchange，里面包含向第一个客户端写响应等动作。

即使其他订阅者等到了流程完成，也不代表它们自己的响应已经被写好。

这次实现通过 `Sinks.One<Optional<byte[]>>` 交付一次填充的结果。有值表示得到了编码后的响应包，空 `Optional` 表示这次结果不能共享。follower 等待的是这个交付信号，而不是重新订阅 leader 的响应 publisher。

这两个「共享」差别很大：

- 共享处理流程，要面对其中绑定了哪个请求、有哪些副作用。
- 共享响应包，则可以把已经得到的结果交给各个请求分别处理。

响应包包含 metadata 的长度、JSON 格式的 metadata，以及原始 body 字节。`CachedResponse.decode` 为每个 follower 复制出自己的 body，`writeTo` 再创建各自的响应缓冲区。它们不共享同一个 `DataBuffer`。

这里还有一个时间上的区别：leader 写响应成功后会发布结果，但并不等缓存写入成功，才允许 follower 复用。**能够交付这次结果，不等于缓存写入已经成功。** 两件事不能混成一个完成信号。

`DataBuffer` 不是一个可以随意交给多个写入者的普通字符串。它有自己的读写状态，某些实现还涉及引用计数和释放。如果多个响应一起消费同一个缓冲区，一个响应的消费或释放就可能影响另一个响应。

因此，这次复用的是**结果内容**，不是同一个正在被消费的缓冲区，也不是同一条向客户端写出的执行链。

取消也需要保持这个边界。一个 follower 放弃等待，不应该因此取消 leader 的回源，让其他仍在等待的请求一起失去结果。各个请求可以等待同一次填充，但它们并没有变成同一个请求。

## 等待一次填充，也要有退出条件

如果只写「后来者都等 leader」，就会留下几个问题：leader 很慢怎么办？响应带有用户 Cookie 怎么办？一个热门 key 挂住大量等待者怎么办？

这次实现选择的是有条件地等待，而不是无限排队。

| 条件                                         | follower 的处理      |
| -------------------------------------------- | -------------------- |
| 等到了可复用的响应包                         | 独立解码并返回       |
| leader 的响应不适合共享，例如带 `Set-Cookie` | 独立回源             |
| 等待超过配置时限                             | 独立回源             |
| 当前 key 的等待名额不足，或协调容量不足      | 不加入等待，独立回源 |
| 响应包超过配置大小                           | 不共享，独立回源     |

响应是否可共享还需要尊重缓存语义。`CachedResponse.capture` 的实际过滤条件是：

```java
if (status < 200 || status == 206 || status == 304 || !response.getCookies().isEmpty()
        || headers.containsKey(HttpHeaders.SET_COOKIE) || headers.containsKey(HttpHeaders.VARY)
        || restrictedCacheControl(headers.getCacheControl())) {
    return Optional.empty();
}
```

`restrictedCacheControl` 会排除 `private`、`no-store`、`no-cache`。但这里**没有 `status >= 300` 的判断**，所以符合其他条件的 404 响应可以被捕获并共享，并不是只有 2xx 才能共享。

PR 正文把 non-2xx 列为不可复用，这一点与最终实现不一致。回归测试 `testFollowerReplaysLeaderStatus` 直接覆盖了 201、404：follower 保留 leader 的状态码、`X-Upstream` 头和 body，上游仍只调用一次。写复盘时，应该以这段实现和已有断言为依据，而不是把正文里的概括当成规则。

leader 出错或被取消时，进行中的协调状态也需要释放。否则后来的请求可能一直看到一个已经失败、却还留在表里的填充者。

follower 的等待链在 `ResponseSingleFlight.follow` 中有明确的退路：

```java
return Optional.of(fill.signal.asMono()
        .defaultIfEmpty(Optional.empty())
        .timeout(waitTimeout)
        .onErrorReturn(Optional.empty())
        .doFinally(ignored -> fill.waiters.decrementAndGet()));
```

超时或错误被转换为空结果，让 follower 回到独立回源路径；响应包解码失败时也会回退。`doFinally` 则归还当前请求的等待名额。这不是取消 leader，而是让一个 follower 退出自己的等待。

配置里有两个容易混淆的时间：

- `singleFlightWaitTimeoutMillis`：follower 愿意等待多久，默认 **1000 毫秒**。
- `singleFlightFillTimeoutMillis`：对一轮填充的协调设置超时，默认 **30000 毫秒**。清理由到达的请求触发，不是后台定时器，也不会因此取消旧回源。

这不是把两个超时合成「所有请求统一等 30 秒」。后来者有自己的等待预算，不能因为 leader 还没有结束，就被迫一直跟着等。

其他默认限制包括每个 key 最多 64 个等待者、共享响应包大小 1 MiB，以及 `singleFlightMaxKeys` 为 1024。1 MiB 限制包括 metadata 和 body，不只是 body；包太大时仍可能写入原来的缓存，只是不用于这次共享。key 容量的判断在并发下是近似限制，不能把它写成严格的全局配额。

回退会重新增加上游请求数，但也给出了一个清晰的取舍：**优先保证请求有退出路径和响应可安全复用，再尽量减少重复回源。** single-flight 不是把任何异常都转化成共享成功，也不是禁止所有独立请求。

## 测试怎样证明请求真的重叠了

如果先完成第一个请求，再发第二个请求，第二个请求命中缓存，上游也只调用一次。这样的测试只能证明缓存正常，不能证明 single-flight 生效。

`CacheSingleFlightTest.testConcurrentMissesShareOneFill` 的关键做法，是让 leader 的填充暂时不完成，再加入同 key 的 follower。

这时可以确认：follower 到达时，缓存结果确实还没生成。随后再放行 leader，检查各个请求得到结果，而上游只执行了一次。

这个「先保留未完成状态，再加入后来者」的顺序，比简单重复调用几次更重要。它把需要协调的空窗固定下来，避免测试实际上只覆盖了普通缓存命中。

已有测试还检查了独立的边界：不同 key 不应合并；关闭功能时仍各自回源；带 Cookie、超出响应大小或等待超时时不能继续强行共享；follower 取消不应破坏其他请求。

这些用例不只是给正常路径凑覆盖率。它们分别在回答：

- 合并的范围有没有扩大？
- 等待能不能退出？
- 一个请求结束，会不会影响其他请求？

它们证明了具体场景中的协调行为，但没有给出吞吐量提高多少的性能基准。不能从「上游调用次数减少」直接写出一个未经测量的性能提升比例。

## 从这次改动能带走的判断

**缓存结果之外，还要考虑进行中的工作。** 缓存 miss 不是一个静止状态；在等待结果写入的这段时间里，可能已经有别的请求承担了同样的工作。是否需要协调，要看这个空窗会不会产生昂贵的重复操作。

**共享值，不等于共享副作用和生命周期。** 多个请求可以复用同一份响应内容，但不应该不加区分地复用第一个请求的执行链、缓冲区或取消信号。

**并发优化要同时说明退路。** 只讲「同 key 只回源一次」会掩盖实现边界。响应能否复用、等待能否超时、容量满时怎么办，决定了这项优化在异常场景里是否仍然可用。

最后，功能默认关闭，需要显式设置 `singleFlightEnabled`。协调也只发生在单个网关实例内：多个副本仍可能各自选出一个 leader，分别填充同一个 key，它不是分布式锁。

这条 PR 没有加入 stale-while-revalidate，也没有建立缓存失效代际来阻止旧填充重新写回已失效的条目。这些是另外的状态管理问题，不能因为 miss 路径有了协调，就认为整个缓存生命周期都已解决。

这次改动最值得记住的，不是 single-flight 这个名字，而是它把「已经有结果」和「已经有人在取结果」分开了。分清这两种状态，才能判断一个后来到达的请求应该复用、等待，还是自己继续执行。
